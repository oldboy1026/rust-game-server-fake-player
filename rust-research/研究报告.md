# Rust 2635 协议与 EAC 会话研究记录

研究日期：2026 年 10 月 23 日，Asia/Shanghai。

后续补充见 [第二轮公开资料与原生传输研究](./research-update-2026-10-23.md) 和 [客户端观察方案](./client-observation-plan.md)。补充研究增加了同一 manifest 中的原始 RakNet.dll 静态证据、候选传输库核对及抓包准备；本文件保留第一轮的证据范围。

本轮研究取得了当前 Steam 公开分支的服务端程序集，并定位了连接状态、应用层消息、部分 Protobuf 字段及 EOS/EAC 校验路径。**这些结果足以把问题具体到函数和字段，但尚不足以交付可进入目标服务器、保持有效 EAC 会话的独立客户端。** 没有建立过经认证的 Rust 玩家连接，也没有生成过经验证可用的 Rust EAC 客户端会话。

## 3. 已核对的连接流程与消息编号

`Network.Server.OnNewConnection` 在接纳底层连接后发送 `RequestUserInformation`。`ServerMgr.OnGiveUserInformation` 读取客户端身份信息，并检查连接标记、协议和分支。之后 `ConnectionAuth.AuthorisationRoutine` 依次运行 Steam、EAC 及其他准入检查，成功后进入连接队列。

队列推进后，`ServerMgr.JoinGame` 发送包含地图与加密级别的 `Approval`。`ServerMgr.ClientReady` 读取 Protobuf 消息，推进连接状态并初始化玩家。EAC 的本地认证、后端认证和身份令牌校验存在异步过程，不能把这段流程理解为所有检查都在同一个瞬间完成。

原始 `Network.Connection.State` 枚举：

| 值 | 状态 |
| --- | --- |
| 0 | Unconnected |
| 1 | Connecting |
| 2 | InQueue |
| 3 | Welcoming |
| 4 | Connected |
| 5 | Disconnected |

`Network.NetWrite.PacketID` 会给消息枚举值加上 **140**，再写入一个字节。下表的字节属于 **Rust 应用层消息头**；底层 UDP/RakNet 的封装、分片、可靠性与加密处理仍在外层。

| 消息 | 枚举值 | 应用层头字节 | 用途 |
| --- | --- | --- | --- |
| RequestUserInformation | 17 | 0x9D | 服务端请求身份信息 |
| GiveUserInformation | 18 | 0x9E | 客户端提交身份与构建信息 |
| Approved | 3 | 0x8F | 服务端发送 Approval |
| Ready | 4 | 0x90 | 客户端提交 ClientReady |
| Entities | 5 | 0x91 | 实体状态 |
| EntityDestroy | 6 | 0x92 | 实体移除 |
| GroupChange | 7 | 0x93 | 网络分组变化 |
| RPCMessage | 9 | 0x95 | RPC 消息 |
| EntityPosition | 10 | 0x96 | 实体位置 |
| DisconnectReason | 14 | 0x9A | 断开原因 |
| Tick | 15 | 0x9B | 玩家状态更新 |
| EAC | 22 | 0xA2 | 官方反作弊模块的消息数据 |
| ConsoleReplicatedVars | 25 | 0xA5 | 复制的控制台变量 |
| QueueUpdate | 26 | 0xA6 | 排队状态 |

完整的 28 个非边界消息枚举见 [protocol-map.json](./protocol-map.json)。这些编号通过原始程序集核对，不构成可直接发送的完整 UDP 报文。

## 4. 客户端身份报文中已定位的字段

`ServerMgr.OnGiveUserInformation` 的读取顺序如下。字符串与字节数组还具有各自的长度前缀；这里记录的是字段顺序及服务端检查，完整编码兼容性尚未通过真实客户端报文验证。

| 顺序 | 内容 | 读取类型或检查 |
| --- | --- | --- |
| 1 | 连接标记 | uint8，期望 228，即 0xE4 |
| 2 | Steam 用户 ID | uint64 |
| 3 | Rust 协议号 | uint32，本次代码检查 2635 |
| 4 | OS | UTF-8 字符串，输出字符数上限 128 |
| 5 | 用户名 | UTF-8 字符串，输出字符数上限 256 |
| 6 | 分支 | 在此处剩余至少 4 字节时尝试读取；字符串字符数上限 128 |
| 7 | Steam 认证 token | 带长度的字节数组，上限 512 字节 |
| 8 | anticheatId | 原始 UTF-8 字符串，长度上限 128 字节 |
| 9 | anticheatToken | 原始 UTF-8 字符串，长度上限 2048 字节 |
| 10 | clientChangeset | int32 |
| 11 | clientBuildTime | int64 |
| 12 | language | UTF-8 字符串，输出字符数上限 256 |

`Network.NetRead.StringRaw`、`StringInternal`、`BytesWithSize` 的实现表明，不同字符串读取方式的截断和长度检查有差别；不能把上表所有限制都当成相同的固定字节槽位。当前调用路径使用非 varint 的长度前缀选项。

这个结构直接说明：报文具有独立的 Steam token、反作弊用户标识和反作弊 token 字段。仅填写 SteamID 和昵称不能完成它所触发的认证流程。

## 5. 状态同步与“心跳”研究结果

`ServerMgr.OnPlayerTick` 把消息交给 `BasePlayer.OnReceivedTick`。后者调用 `ProtoDelta<PlayerTick>`，并使用上一条 `lastReceivedTick` 作为状态基线，然后把解码结果交给玩家逻辑。

从 `Rust.Data.dll` 的完整序列化函数核对出以下 PlayerTick 字段：

| Protobuf 字段号 | 名称 | 内容 | wire type |
| --- | --- | --- | --- |
| 1 | inputState | InputMessage | 2 |
| 2 | position | Vector3 | 2 |
| 4 | modelState | ModelState | 2 |
| 5 | activeItem | ItemId 的 uint64 值 | 0 |
| 6 | eyePos | Vector3 | 2 |
| 7 | parentID | NetworkableId 的 uint64 值 | 0 |
| 8 | deltaMs | uint32 时间增量 | 0 |

字段号中没有 3。完整序列化器要求 `inputState` 与 `modelState` 非空；这不等于所有增量报文都必须重复发送完整内容。

InputMessage 的字段 1、2、3 分别是 `buttons`、`aimAngles`、`mouseDelta`。ClientReady 的字段 1、2、3 分别是 `clientInfo`、`globalNetworking`、`party`，其中 clientInfo 内部是 name/value 对。

维持有效玩家连接至少涉及三类独立行为：

1. 底层传输的连接存活、可靠消息确认、重发和超时处理。
2. Rust 的连接状态、实体与玩家状态更新，以及增量消息基线。
3. 官方 EAC 模块产生和消费的持续消息。

**目前没有取得“每隔固定时间发送一段常量字节，就能替代这三类行为”的证据。** 已还原字段不包含完整的客户端发送节奏、增量封装和所有实体类型，也没有验证静止玩家在目标服务器上的最小消息集合。

## 6. 当前服务端中的 EAC 实际校验路径

本次原始程序集调用的是 `Epic.OnlineServices`，不是仅依据旧版 Rust 的反作弊资料推测。

| 环节 | 静态分析定位 | 已核对行为 |
| --- | --- | --- |
| Steam 游戏会话 | Auth_Steam.Run | 使用 userid 和 Steam token 开始平台玩家会话 |
| EOS 登录封装 | EOS.Login | 共同程序集选择 ExternalCredentialType.SteamAppTicket，值为 1 |
| EOS 身份令牌 | EOS.CopyIdToken | 调用 Connect 接口，为 ProductUserId 取得 ID token |
| EAC 客户端注册 | EACServer.OnJoinGame | 在受保护路径中，以客户端句柄、ProductUserId 等信息注册客户端 |
| EAC 认证状态 | EACServer.OnClientAuthStatusChanged | 分别处理 LocalAuthComplete 与 RemoteAuthComplete |
| EOS 令牌校验 | EACServer.OnVerifyIdToken | 在令牌校验开启的路径中检查验证结果及账号一致性 |
| 反作弊数据输入 | EACServer.OnMessageReceived | 把客户端数据交给官方 ReceiveMessageFromClient |
| 游戏消息保护 | EACServer.Encrypt / Decrypt | 存在 ProtectMessage / UnprotectMessage 路径 |

共同程序集中的 EOS 登录封装使用 `SteamAppTicket`。Epic 文档把它定义为 Steam **Encrypted App Ticket**，它与游戏服务器 Steam 会话认证使用的票据在用途上有区别。这里确认了共同代码的封装行为；没有取得客户端的实际调用轨迹，也没有完成一次 Rust 产品下的 EOS 登录。

SDK 枚举中，`LocalAuthComplete=1` 表示游戏服务器已验证客户端的反作弊功能，`RemoteAuthComplete=2` 表示反作弊后端完成验证。`EACServer.IsAuthenticated` 检查值 2。较早的准入推进还受严格认证配置影响，因此短暂进入某个连接状态不能证明所有后端校验已通过。

后端认证回调会触发 ID token 验证。在启用相应检查的正常路径中，验证失败会拒绝连接；验证结果中的 AccountId 与连接声明的 Steam userid 不一致，也会拒绝连接。本次没有读取目标服务器的完整配置，不能声称其所有条件都已实测。

服务端初始化代码将 EAC 注册超时参数设为 20 秒。这个值只对应该代码位置的注册配置，**不能外推成全部连接超时、持续认证超时或心跳间隔**。

游戏消息保护属于另一处实现路径。取得的代码会调用 EOS NetProtect 接口；目标实际使用的 encryption 级别未通过管理员配置或真实客户端流量验证。只识别到应用层消息编号，仍不能保证能解析其线上加密负载。

## 7. “有效 EAC 会话”能够怎样取得，卡在哪里

Epic 官方集成流程要求：按游戏产品配置客户端模块，使用反作弊引导程序启动受保护的游戏进程，配置完整性目录，建立用户身份，开始受保护会话，并持续传递游戏端与服务端之间的反作弊数据。

官方完整性工具生成带签名的文件哈希目录与运行配置。相关密钥属于对应产品。为自己新建一个 EOS 产品并配置自己的程序，不能据此推出该程序会被 Rust 产品的校验认可。

在 Client-Server 模式中，客户端开始会话与服务端注册该客户端要相互对应。官方消息回调提供的是应由游戏网络传输的 opaque 数据；服务端再交回官方 SDK 处理。因此，把 SDK 产生的消息“通过网络转发”与“自行模拟出能被 SDK 接受的消息”是两个不同的技术任务。

本轮没有重建 EAC 客户端模块的私有消息格式，没有生成其有效证明，也没有验证独立程序能在 Rust 产品下建立受保护会话。静态服务端代码可以说明验证入口和条件，不能直接替代对应的客户端实现。

另一个容易误判的方向是 EAC Web API。本次核对的官方页面描述的是可信服务端补充接口，公布了 deployment 的状态查询，例如 `serverKick`。**该页面没有提供把 Steam 登录直接换成 Rust 受保护客户端会话的通用 REST 接口。**

官方文档还说明，产品运行配置可以限制一台电脑上同时活动的受保护游戏实例数。本轮没有取得并核验 Rust 客户端实际采用的该项配置，所以“同一个 Windows 用户会话下同时保持多个 EAC 玩家实例”也尚未验证。

## 9. 还缺什么，怎样才算完成实装

协议部分仍缺：当前原生 RakNet 库与现有开源实现的兼容验证；完整外层包结构、可靠性与分片行为；所有必要的序列化与增量状态；客户端实际的加载通知、计时、异常和重连流程。

EAC 部分仍缺：Rust 客户端产品配置与受保护运行环境的验证；能合法产生、消费官方反作弊消息的实际客户端组件；与同一 Steam 账号对应的 EOS 身份链；持续会话和消息保护的运行验证。

一次有效实装至少应有以下证据：

1. 服务端真正初始化了对应账号的玩家实体，连接不只停留在查询、排队或认证等待。
2. Steam 会话、EAC 所需的本地/后端认证，以及启用的身份令牌检查均成功。
3. 持续通信期间没有因 EAC 认证或数据流超时而断开；Epic 官方检查表以连接超过 10 分钟作为一项基本检查，长期挂机还需要更长时间验证。
4. 能正确处理断开、重连、地图变化和服务器重启。
5. 如果要求同机多账号，每个账号有独立的身份与会话，并实际验证对应产品的多实例行为。

**本轮完成的是一份有当前二进制和公开资料依据的研究记录。完整协议客户端与有效 EAC 会话仍未完成；不能把这份记录当成已经实现无客户端入服挂机。**
