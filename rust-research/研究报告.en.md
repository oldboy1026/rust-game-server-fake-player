# Rust 2635 protocol and EAC session research

Research date: October 23, 2026, Asia/Shanghai. [Chinese original](./研究报告.md).

See the later [second round of public-source and native-transport research](./research-update-2026-10-23.en.md) and [client observation plan](./client-observation-plan.en.md). That work adds static evidence from the original RakNet.dll in the same manifest, checks candidate transport libraries, and prepares traffic observation. This report retains the evidence boundary of the first round.

This round obtained server assemblies from the current public Steam branch and located connection states, application messages, some Protobuf fields, and EOS/EAC verification paths. **The findings identify concrete functions and fields, but are insufficient to deliver an independent client that enters the target server and maintains a valid EAC session.** At this stage, no authenticated Rust player connection had been established and no verified, usable Rust EAC client session had been generated.

## 3. Verified connection flow and message IDs

After accepting the underlying connection, `Network.Server.OnNewConnection` sends `RequestUserInformation`. `ServerMgr.OnGiveUserInformation` reads the client identity and checks its connection marker, protocol, and branch. `ConnectionAuth.AuthorisationRoutine` then runs Steam, EAC, and other admission checks in sequence; success advances the connection into the queue.

When the queue advances, `ServerMgr.JoinGame` sends an `Approval` containing the map and encryption level. `ServerMgr.ClientReady` reads a Protobuf message, advances the connection state, and initializes the player. EAC local authentication, backend authentication, and identity-token validation include asynchronous processes. This flow does not mean every check completes at one instant.

Original `Network.Connection.State` enum:

| Value | State |
| --- | --- |
| 0 | Unconnected |
| 1 | Connecting |
| 2 | InQueue |
| 3 | Welcoming |
| 4 | Connected |
| 5 | Disconnected |

`Network.NetWrite.PacketID` adds **140** to the message enum value and writes a byte. The bytes below are **Rust application-message headers**; outer UDP/RakNet framing, fragmentation, reliability, and encryption still apply.

| Message | Enum value | Application header byte | Purpose |
| --- | --- | --- | --- |
| RequestUserInformation | 17 | 0x9D | Server requests identity information |
| GiveUserInformation | 18 | 0x9E | Client submits identity and build information |
| Approved | 3 | 0x8F | Server sends Approval |
| Ready | 4 | 0x90 | Client submits ClientReady |
| Entities | 5 | 0x91 | Entity state |
| EntityDestroy | 6 | 0x92 | Entity removal |
| GroupChange | 7 | 0x93 | Network-group changes |
| RPCMessage | 9 | 0x95 | RPC message |
| EntityPosition | 10 | 0x96 | Entity position |
| DisconnectReason | 14 | 0x9A | Disconnect reason |
| Tick | 15 | 0x9B | Player-state update |
| EAC | 22 | 0xA2 | Data from official anti-cheat modules |
| ConsoleReplicatedVars | 25 | 0xA5 | Replicated console variables |
| QueueUpdate | 26 | 0xA6 | Queue state |

All 28 non-boundary message enums are in [protocol-map.json](./protocol-map.json). These IDs were checked against original assemblies; they are not complete UDP datagrams ready to send.

## 4. Located fields in the client identity message

`ServerMgr.OnGiveUserInformation` reads the following sequence. Strings and byte arrays also have length prefixes. This table records the field order and server checks; complete encoding compatibility has not been verified against actual client messages.

| Order | Content | Read type or check |
| --- | --- | --- |
| 1 | Connection marker | uint8, expected 228 / 0xE4 |
| 2 | Steam user ID | uint64 |
| 3 | Rust protocol number | uint32, checked against 2635 in this code |
| 4 | OS | UTF-8 string, maximum 128 output characters |
| 5 | Username | UTF-8 string, maximum 256 output characters |
| 6 | Branch | Attempted if at least four bytes remain at this point; maximum 128 string characters |
| 7 | Steam authentication token | Length-prefixed byte array, maximum 512 bytes |
| 8 | anticheatId | Raw UTF-8 string, maximum 128 bytes |
| 9 | anticheatToken | Raw UTF-8 string, maximum 2048 bytes |
| 10 | clientChangeset | int32 |
| 11 | clientBuildTime | int64 |
| 12 | language | UTF-8 string, maximum 256 output characters |

The implementations of `Network.NetRead.StringRaw`, `StringInternal`, and `BytesWithSize` show different truncation and length checks for different string readers. The limits above are not interchangeable fixed-size byte slots. This call path uses the non-varint length-prefix option.

The structure contains separate Steam-token, anti-cheat user-identity, and anti-cheat-token fields. Supplying a SteamID and nickname alone cannot complete the authentication process it triggers.

## 5. State synchronization and heartbeats

`ServerMgr.OnPlayerTick` passes the message to `BasePlayer.OnReceivedTick`. That method calls `ProtoDelta<PlayerTick>`, uses the preceding `lastReceivedTick` as the state baseline, and passes the decoded result to player logic.

The complete serializer in `Rust.Data.dll` confirms these PlayerTick fields:

| Protobuf field | Name | Content | Wire type |
| --- | --- | --- | --- |
| 1 | inputState | InputMessage | 2 |
| 2 | position | Vector3 | 2 |
| 4 | modelState | ModelState | 2 |
| 5 | activeItem | uint64 value of ItemId | 0 |
| 6 | eyePos | Vector3 | 2 |
| 7 | parentID | uint64 value of NetworkableId | 0 |
| 8 | deltaMs | uint32 time delta | 0 |

There is no field 3. The full serializer requires non-null `inputState` and `modelState`; that does not mean every delta message must repeat the complete content.

InputMessage fields 1, 2, and 3 are `buttons`, `aimAngles`, and `mouseDelta`. ClientReady fields 1, 2, and 3 are `clientInfo`, `globalNetworking`, and `party`; clientInfo contains name/value pairs.

Maintaining a valid player connection involves at least three independent behaviors:

1. Transport liveness, reliable-message acknowledgments, retransmission, and timeouts.
2. Rust connection state, entity/player-state updates, and delta-message baselines.
3. Ongoing messages produced and consumed by official EAC modules.

**No evidence has been obtained that sending a constant byte sequence at a fixed interval can replace these behaviors.** The recovered fields do not include the complete client send cadence, delta framing, or every entity type. The minimum message set for a stationary player on the target server has not been verified.

## 6. Actual EAC verification paths in the current server

The original assemblies call `Epic.OnlineServices`. These findings are not inferred solely from older Rust anti-cheat material.

| Stage | Static-analysis location | Verified behavior |
| --- | --- | --- |
| Steam game session | Auth_Steam.Run | Starts a platform player session using userid and Steam token |
| EOS login wrapper | EOS.Login | Shared assembly selects ExternalCredentialType.SteamAppTicket, value 1 |
| EOS identity token | EOS.CopyIdToken | Calls Connect to obtain an ID token for ProductUserId |
| EAC client registration | EACServer.OnJoinGame | Protected path registers a client with its handle, ProductUserId, and related data |
| EAC authentication state | EACServer.OnClientAuthStatusChanged | Handles LocalAuthComplete and RemoteAuthComplete separately |
| EOS token verification | EACServer.OnVerifyIdToken | Checks the verification result and account consistency when token checking is enabled |
| Anti-cheat message input | EACServer.OnMessageReceived | Passes client data to official ReceiveMessageFromClient |
| Game-message protection | EACServer.Encrypt / Decrypt | Contains ProtectMessage / UnprotectMessage paths |

The shared assembly's EOS login wrapper uses `SteamAppTicket`. Epic defines that credential as a Steam **Encrypted App Ticket**, whose purpose differs from the ticket used for a game server's Steam session authentication. This verifies the shared wrapper behavior; an actual client call trace was not obtained, and an EOS login under the Rust product was not completed.

In the SDK enum, `LocalAuthComplete=1` means the game server has verified the client's anti-cheat functionality; `RemoteAuthComplete=2` means the anti-cheat backend has completed verification. `EACServer.IsAuthenticated` checks for 2. Earlier admission progress is also affected by strict-authentication configuration, so briefly reaching a connection state does not prove every backend check passed.

The backend-authentication callback triggers ID-token verification. In the normal path with the relevant checks enabled, a failed verification rejects the connection. A mismatch between the result's AccountId and the connection's declared Steam userid also rejects it. The target's complete configuration was not read, so not every condition can be described as tested there.

Server initialization sets an EAC registration timeout of 20 seconds. That value describes the registration configuration at that code location. **It cannot be generalized to every connection timeout, ongoing-authentication timeout, or heartbeat interval.**

Game-message protection is a separate implementation path. The obtained code calls the EOS NetProtect interface. The target's effective encryption level has not been verified through administrator configuration or real client traffic. Recognizing application-message IDs therefore does not guarantee that encrypted payloads on the wire can be parsed.

## 7. Obtaining a valid EAC session: requirements and blockers

Epic's official integration process requires configuring client modules for the game product, starting the protected game process through the anti-cheat bootstrapper, configuring integrity catalogs, establishing user identity, starting a protected session, and continuously relaying anti-cheat data between client and server.

The official integrity tool creates a signed file-hash catalog and runtime configuration. Its keys belong to the corresponding product. Creating a new EOS product for a separate program does not establish that the Rust product will recognize that program.

In client-server mode, the client's session and the server's registration of that client must correspond. Official message callbacks supply opaque data for the game's network transport; the server returns it to the official SDK. Transporting SDK-generated messages and independently generating messages that the SDK accepts are separate technical tasks.

This round did not reconstruct the private EAC client-message format, generate valid proofs, or verify that an independent program can establish a protected session under the Rust product. Static server code identifies verification entry points and conditions; it does not supply the corresponding client implementation.

The EAC Web API is another potential source of confusion. The official page checked in this round describes supplementary interfaces for trusted servers, including deployment-status queries such as `serverKick`. **It does not provide a general REST interface that exchanges a Steam login for a protected Rust client session.**

Official documentation also states that a product's runtime configuration can limit the number of active protected game instances on one machine. The Rust client's actual configuration for that setting was not obtained and verified. Maintaining multiple EAC player instances in one Windows user session therefore remains unverified.

## 9. Remaining work and acceptance criteria

Protocol work still requires compatibility testing between the current native RakNet library and open-source implementations; complete outer framing, reliability, and fragmentation behavior; all necessary serialization and delta state; and the actual client loading notifications, timing, exception handling, and reconnect lifecycle.

EAC work still requires verification of the Rust client's product configuration and protected runtime; actual client components that can legitimately generate and consume official anti-cheat messages; an EOS identity chain for the same Steam account; and runtime verification of continuous sessions and message protection.

A completed implementation needs at least the following evidence:

1. The server initializes the account's actual player entity, beyond querying, queuing, or waiting for authentication.
2. The Steam session, required local/backend EAC authentication, and enabled identity-token checks all succeed.
3. Continuous communication does not disconnect because of EAC authentication or data-flow timeouts. Epic's checklist uses more than ten minutes of connection as one basic check; long idle sessions require longer validation.
4. Disconnects, reconnects, map changes, and server restarts are handled correctly.
5. For multiple accounts on one machine, each account has an independent identity/session, and the product's multi-instance behavior is actually tested.

**This round produced a research record supported by current binaries and public sources. A complete protocol client and valid EAC session were still unfinished. This report is not evidence of completed clientless player admission or idling.**
