## How one computer can appear at different IPs and ports

The reported topology is possible. The controller's physical computer and server-visible egress need not be identical:

```text
One Windows computer
  ├─ Session A ─ multi-IP routing / UDP relay / tunnel exit A ─ Rust server
  ├─ Session B ─ multi-IP routing / UDP relay / tunnel exit B ─ Rust server
  └─ Session C ─ multi-IP routing / UDP relay / tunnel exit C ─ Rust server
```

|Behavior|Possible network explanation|What it does not establish|
|---|---|---|
|Different ports|Separate sockets and source ports; NAT port rewriting|Independent game processes|
|Different public IPs|Multiple routed addresses, address pools, UDP relays, or tunnel exits|A particular SOCKS5 implementation or all execution occurring on the controller|
|Bulk control from one computer|One controller managing several session state machines|Absence of remote workers or hidden game processes|
|Updating player lists|Changing published query/player information, possibly driven by real active sessions|Complete gameplay state or valid EAC sessions|

[RFC1928 section 7](https://www.rfc-editor.org/rfc/rfc1928#section-7) defines SOCKS5 UDP relaying; [RFC4787 section 4.1](https://www.rfc-editor.org/rfc/rfc4787#section-4.1) discusses NAT address/port mapping and public-address pools. These support feasibility, **not evidence identifying this server's actual implementation**. Ordinary HTTP CONNECT does not automatically relay UDP.

Changing a packet's source IP alone does not establish a return path. Normal Rust connections require bidirectional traffic, with replies routed through the exit back to the correct session. Multi-exit session management is distinct from one-way source-address spoofing.

## Which server-log field needs verification

Static evidence from the researched assemblies shows new RakNet connections passing Network.NetRead.ipaddress to Network.Server.OnNewConnection(UInt 64, String), then Network.Connection.ipaddress. The native address accessor is NET_GetAddress. These findings apply to the analyzed version; the new target's transport/binaries were not confirmed.

A plugin logging player.net.connection.ipaddress normally records the remote address known to game transport rather than a player name or Steam profile address. Through a relay, it may see the relay exit. Custom fields require examination of the logging code. That code/field was unavailable, so no underlying packet correlation was claimed.

## Implications

Independent session management, multiple network exits, and server-count publication are separate hypotheses to verify. Different IPs/ports describe network identity; Steam tickets, Rust application protocol, and actually enforced EAC checks each require their own evidence. Network exits do not supply these missing states.

The most useful next material would be sanitized server connection logs or the plugin section that records addresses and presence: times, anonymized account aliases, the actual remote-address field, disconnect reasons, and whether entries are normal active players. Tickets, cookies, login tokens, and unsanitized bulk identities must not be committed.

Public registration matched the supplied query/game ports and network analysis was established. The Rust implementation, session execution location, and EAC handling were not identified. No player login, protocol simulation, source spoofing, or EAC authentication was performed in this round.
