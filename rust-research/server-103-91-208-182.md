## 一台电脑为何能表现为不同 IP 和端口

用户描述的网络结构是可行的。控制程序所在的电脑与服务器看到的网络出口可以不同：

```text
一台 Windows 电脑
  ├─ 独立会话 A ─ 多 IP 路由 / UDP 中继 / 隧道出口 A ─ Rust 服务器
  ├─ 独立会话 B ─ 多 IP 路由 / UDP 中继 / 隧道出口 B ─ Rust 服务器
  └─ 独立会话 C ─ 多 IP 路由 / UDP 中继 / 隧道出口 C ─ Rust 服务器
```

| 现象 | 网络层可以怎样实现 | 不能据此确认什么 |
| --- | --- | --- |
| 每账号不同端口 | 多个 socket 使用不同源端口；NAT 也可改写端口 | 不证明使用了独立游戏进程 |
| 每账号不同公网 IP | 主机拥有多个可路由地址、出口地址池、支持 UDP 的中继或隧道等 | 不证明具体用了 SOCKS5，也不证明会话实际都在控制电脑执行 |
| 一台电脑批量控制 | 一个控制程序管理多组连接和会话状态 | 不证明没有远程工作进程或隐藏游戏进程 |
| 玩家列表持续更新 | 对外查询信息或玩家资料持续变化；真正活跃会话也可驱动它 | 单凭列表不能验证完整游戏状态或 EAC 会话 |

[RFC 1928](https://www.rfc-editor.org/rfc/rfc1928#section-7)定义 SOCKS5 的 UDP 中继；[RFC 4787](https://www.rfc-editor.org/rfc/rfc4787#section-4.1)解释 NAT 地址/端口映射，也描述多个公网出口地址的地址池。这些资料支持上述网络结构的可行性，**没有证据表明该服务器的控制程序实际使用了其中哪一种方式。** 普通 HTTP CONNECT 代理不自动具有 UDP 转发能力。

只改数据包中的源 IP，不会自动建立正确的回程路径。Rust 的正常连接需要收发双方的数据；服务器回包应当能经过所用出口返回相应会话。应将这种多出口会话结构与单向伪造源地址分清。

## 服务端日志中的地址需要对应哪个字段

现有原始程序集静态证据显示：RakNet 的新连接处理将 `Network.NetRead.ipaddress` 交给 `Network.Server.OnNewConnection(UInt64, String)`，再写入 `Network.Connection.ipaddress`；原生地址查询入口为 `NET_GetAddress`。这些信息来自研究版本，尚未确认新目标使用的传输和二进制。

如果管理员插件直接记录 `player.net.connection.ipaddress`，通常记录的是游戏传输连接所知的远端地址，而不是玩家名字或 Steam 个人资料中的地址。经过中继时，服务器可能看到中继的出口。若插件记录的是自定义字段，则需要读取插件对应代码才能解释。此次没有取得这个字段，不能声称已经完成底层数据包核对。

## 对后续研究的影响

现象可以由“独立会话管理 + 多网络出口 + 服务器人数发布”这一结构解释，应把它们作为分别需要确认的环节。不同 IP/端口解决的是网络连接身份；Steam 账号票据、Rust 应用协议和实际执行的 EAC 验证仍各自需要证据，网络出口不会自动补齐这些状态。

最有用的下一份材料是经过脱敏的服务端连接日志，或插件中记录地址和在线状态的那段代码：包括时间、匿名化账号标识、实际远端地址字段、断开原因、是否为正常活跃玩家。不要将认证票据、Cookie、登录令牌或未脱敏的真实账号批量信息提交到仓库。

目前已确认公开登记端口与用户提供值一致，并建立了网络层分析依据；尚未识别该程序的 Rust 协议实现、会话运行位置或 EAC 处理方式。本轮没有执行玩家登录、协议模拟、源地址伪造或 EAC 认证。
